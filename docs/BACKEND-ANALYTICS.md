# Backend — Platform Analytics & Reporting (Phase 6)

Single reporting center for the platform. The frontend renders one aggregated
response scoped by the caller's role; the backend is responsible for enforcing
scope, joining across modules, and generating exports.

## Endpoints

### `GET /v1/analytics/platform`
Returns the aggregated `PlatformAnalytics` payload (see
`src/types/analytics.ts`). Scope is derived from the JWT role:

| Role              | scope           | Data returned                                         |
| ----------------- | --------------- | ----------------------------------------------------- |
| Super Admin       | `platform`      | Whole platform                                         |
| Campaign Manager  | `organization`  | Only entities owned by the caller's organization       |
| Volunteer         | `personal`      | Only `personal` block populated; module blocks zeroed  |
| Viewer            | 403             | Route is denied at the frontend and API layers         |

Query parameters (all optional, all comma-separated for arrays):

- `from`, `to` — ISO-8601 dates. Default: last 30 days.
- `campaign_ids`, `disaster_ids`, `organization_ids`, `volunteer_ids`
- `languages` — BCP-47 codes (`en,hi,ta`)

### `POST /v1/analytics/exports`
Async export orchestration. Request body:

```json
{
  "dataset": "platform | campaigns | qr | volunteers | disasters | multilingual | public_engagement",
  "format":  "csv | xlsx | pdf | json",
  "filters": { ... same filter shape as /platform ... }
}
```

Response: `ExportResult` with a signed URL. The URL should be single-use and
expire within 15 minutes.

Requires permission `analytics:export`.

## Recommended data layer

Aggregations should be served from **materialized views** refreshed on a
5-minute schedule (or triggered by domain events). Suggested views:

- `mv_campaign_analytics_daily`  — grain: day × campaign × organization
- `mv_qr_scan_analytics_daily`   — grain: day × campaign × country × device × language
- `mv_volunteer_activity_daily`  — grain: day × volunteer × organization
- `mv_disaster_analytics_daily`  — grain: day × disaster × severity
- `mv_multilingual_daily`        — grain: day × language × status × entity_type
- `mv_public_engagement_daily`   — grain: day × entity_type × language

The `/v1/analytics/platform` endpoint composes its response by aggregating
these views under the caller's scope; no per-request cross-table joins on
transactional tables.

## Performance & optimisations

1. **Materialized views** as above; refresh via `pg_cron`.
2. **Row-level scope** enforced by a SQL function `analytics_scope(user_id)`
   returning organization/volunteer identifiers.
3. **Response caching** — cache the platform payload per `(user_id, filters
   hash)` for 60s in Redis.
4. **Streaming exports** — CSV/PDF/XLSX generated by a worker (RQ or Celery)
   and uploaded to S3-compatible storage; the URL returned is a presigned S3
   URL. Never stream large exports through the HTTP request/response cycle.
5. **Filter indexes** — add composite indexes matching the mv grain
   (`(day, organization_id, campaign_id)` etc.).

## SQLAlchemy models (sketch)

```python
class CampaignAnalyticsDaily(Base):
    __tablename__ = "mv_campaign_analytics_daily"
    day = Column(Date, primary_key=True)
    campaign_id = Column(UUID, primary_key=True)
    organization_id = Column(UUID, index=True)
    published = Column(Integer, default=0)
    archived = Column(Integer, default=0)
    reach = Column(BigInteger, default=0)
    engagement_rate = Column(Numeric(5, 4), default=0)
    downloads = Column(Integer, default=0)

class QrScanAnalyticsDaily(Base):
    __tablename__ = "mv_qr_scan_analytics_daily"
    day = Column(Date, primary_key=True)
    campaign_id = Column(UUID, primary_key=True)
    country = Column(String(2), primary_key=True)
    device = Column(String(16), primary_key=True)
    language = Column(String(8), primary_key=True)
    scans = Column(Integer, default=0)
    unique_visitors = Column(Integer, default=0)
```

Analogous models for volunteer / disaster / multilingual / public engagement.

## Alembic migration outline

1. `create materialized view mv_campaign_analytics_daily as ...`
2. Repeat for each of the five views above.
3. `create unique index on mv_* (day, ...primary key columns)` — required for
   `refresh materialized view concurrently`.
4. `select cron.schedule('mv_analytics_refresh', '*/5 * * * *', $$ refresh
   materialized view concurrently mv_campaign_analytics_daily; ... $$);`
5. Table `analytics_exports (id, user_id, dataset, format, filters, status,
   url, expires_at, created_at)` for tracking async jobs.

## RBAC mapping

- `analytics:view`  — required for `GET /v1/analytics/platform`.
- `analytics:export` — required for `POST /v1/analytics/exports`.

Backend must enforce scope even when the caller passes filters outside their
scope (silently intersect; never leak cross-org data).
